# 3. Design decisions

Each decision is written ADR-style: what was chosen, what else was considered, and the trade-off accepted.

| # | Decision | Alternatives considered | Why / trade-off |
|---|---|---|---|
| DD-01 | **React Native with Expo (SDK 58, New Architecture, Hermes)** for one iOS + Android codebase | Native Swift + Kotlin; Flutter; responsive web/PWA | One TypeScript codebase and skill set shared with the backend. Expo modules cover file picking, secure storage, crypto and push without custom native code. EAS Build/Submit/Update gives signed builds and staged OTA fixes. A PWA cannot reliably do background uploads, push on iOS or Keychain storage. *Trade-off:* native modules outside Expo need a dev build (already the plan for release). |
| DD-02 | **Mobile-first, not a web SPA**, while keeping the web door open | Web SPA (as the brief suggests) | The users are store managers on the shop floor. The same code runs on react-native-web, so an HQ web console can follow without a rewrite. |
| DD-03 | **Direct-to-S3 upload with a pre-signed URL, then asynchronous ingestion** | Multipart POST through the API; synchronous parse-and-save | Large files on flaky store networks should not tie up API instances or hit gateway timeouts. Uploads resume in the background, and processing scales independently on queue depth. *Trade-off:* the user waits for a status (polling or push) instead of an instant answer. The on-device pre-check covers the common mistakes up front. |
| DD-04 | **Idempotency end to end**: file SHA-256 per uploader, natural-key upsert on `(store, SKU, effective date)`, unchanged rows skipped | Rely on exactly-once delivery; dedupe by file name | SQS and retries are at-least-once. The same file or message can arrive twice without double-applying or bumping versions. |
| DD-05 | **Partial acceptance with row-level rejects**. Only a bad header fails the whole file | All-or-nothing transaction per file | One bad row should not block 29,999 good prices. Every rejected row is reported with its line number and reasons so the store can fix only those. |
| DD-06 | **PostgreSQL (Aurora) as system of record**, partitioned by country and month. Search uses composite indexes + `pg_trgm`. OpenSearch only if needed (CDC) | DynamoDB; search-engine-first; one big unpartitioned table | Search is ad-hoc across several criteria, and edits need transactions with their audit rows. A relational model fits both. Partitioning keeps indexes small, prunes country-scoped queries and makes retention a partition drop. *Trade-off:* fuzzy multilingual search is weaker than OpenSearch, so it is planned as a phase-2 read model. |
| DD-07 | **Keyset (cursor) pagination, no total counts** | OFFSET/LIMIT with `COUNT(*)` | OFFSET gets slower with every page and `COUNT(*)` is expensive at 90M+ rows. Infinite scroll on mobile doesn't need a total. |
| DD-08 | **Optimistic concurrency**: `version` column, `ETag` / `If-Match`, `412` with the current record | Last write wins; pessimistic locks | Prevents lost updates between a feed and a person, or two people. Locks are a bad fit for mobile clients that go offline. The conflict UI lets the user choose deliberately. |
| DD-09 | **Append-only audit trail and transactional outbox** | Audit via logs; publish events directly from code | Price changes are business- and compliance-relevant: who, what, when and why. The outbox makes "saved and published" atomic. |
| DD-10 | **Regional cells** (EU, APAC, NA, MEA) with the same infrastructure-as-code | One global deployment; per-country deployments | Meets data-residency rules (e.g. GDPR) and contains failures. Per-country stacks would multiply operations cost about 15×. |
| DD-11 | **Security model**: OIDC Authorization Code + PKCE, short-lived access tokens in Keychain/Keystore, **row-level scope enforced in SQL** on every query | API keys; client-side filtering; session cookies | Never trust a client filter: even a crafted request can only see its own scope. Scope comes from IdP claims and maps to the store hierarchy. |
| DD-12 | **Money as `NUMERIC` and decimal strings end to end. Currency comes from the store master**, not the file | Floats; a currency column in the CSV | Avoids rounding errors, and a mistyped currency in a file cannot mis-price a store. |
| DD-13 | **Strict, explicit feed contract**: header by name (any order, common aliases), UTF-8 (BOM tolerated), ISO-8601 dates, `.` decimal separator | Guess formats per country | `01/02/2026` is ambiguous across countries. Rejecting it with a clear message is safer than guessing, and the message tells the user exactly what to change. |
| DD-14 | **Server state in TanStack Query** (persisted), local UI state in components. No Redux | Redux Toolkit / RTK Query; MobX | Nearly all state is server state. TanStack Query gives caching, retries, offline pause and persistence with very little code. |
| DD-15 | **Modular monolith API plus a separate worker deployment** from one codebase | Microservices per capability | The team and the domain are small. Module boundaries (`feeds`, `prices`, `stores`, `auth`) are explicit, so they can be split out later without a rewrite. |
| DD-16 | **Ports and adapters for infrastructure**: `Database`, `BlobStore`, `JobQueue`. Local adapters are PGlite (embedded PostgreSQL), disk storage and an in-process queue | Docker-only local setup | Reviewers can run everything with `npm install && npm run dev`, against the same SQL that runs on Aurora. Production adapters (pg, S3, SQS) sit behind the same interfaces. |
| DD-17 | **Release safety for mobile**: EAS Update channels with staged rollout, a minimum-supported-version check, feature flags | Store releases only | JS fixes reach 3,000 stores in hours, not days of review. Native changes still go through store or MDM releases. |
